# Comment protocol v1

The Chrome extension supports three bounded, strictly validated record types. Use a top-level fenced code block in a PR/issue description or conversation comment; examples inside blockquotes are intentionally ignored. Current limits: 100 KB per record, nesting depth 16, no YAML alias expansion or duplicate mapping keys, 60 questions, 50 choices/question, 300 beads/snapshot, 16,000 characters per normal text field. Unknown fields and versions fail closed. No raw HTML form definitions, scripts, workflow names, executable operations or arbitrary endpoint fields are accepted.

## Form (`github-task`)

Required: `format: "standard"`, `id`, `title`, `questions`. `version` is 1 (default). Optional: `kind: "form"`, `goal`, `description`, `task_id`, `session_id`, `parent_task_id`, `invalidatedAt`, `invalidatedReason`, `allowCodeFileChanges`, `nextInstructionPresets`.

IDs begin with a letter and contain letters, numbers, `_` or `-`, maximum 100 characters. IDs and generated answer names must be unique. `next_instruction` and `allow_code_file_changes` are reserved.

Questions share `id`, `title`, `description` (defaults empty) and optional `required`:

- `type: "textarea"` or `"text"`, optional `placeholder`.
- `type: "choices"`, `choices: [{id, label, description?, is_recommended_reason?, assumedTrue?, prosAndCons?: {pros?: string[], cons?: string[]}}]`. Choices are always checkboxes. `assumedTrue` is explanatory, never a preselection.
- Optional `choiceGroups: [{id, title?, description?, mode: "any" | "atMostOne" | "exactlyOne", choiceIds: string[]}]`. Selecting an exclusive option clears its peers; exactly-one membership is validated at preview time.

Every choice/question has optional More info notes. `additional_notes` is the master textarea and has no redundant nested notes. Next Instruction is an independent textarea, with optional `{label, value}` presets. Safe Markdown supports contextual text without executing HTML. A form with `invalidatedAt` is displayed as superseded and cannot be answered.

`allowCodeFileChanges: false` exposes only discussion intent. Otherwise its optional object supports `allowLabel`, `avoidLabel`, `label`, `description`, `defaultChecked` (accepted for authoring compatibility, never grants implicit permission). Approval requires the explicit button action.

## Response (`github-response`)

Generated by the extension as pretty JSON, preceded by a slash-command line:

```text
/github-ultimate discuss
```

or `/github-ultimate approve`. Command parsing/execution belongs to a future trusted handler. Form submission generates the command; inserting it does not submit it or run anything.

Fields: `schema_version: 1`, `kind: "response"`, unique `response_id`, `task_id`, `form_id`, nullable `session_id`/`parent_task_id`, `source: {repository, number, comment_id, revision}`, `intent`, `resume_session`, `allow_code_file_changes`, `answers`.

The SHA-256 `source.revision` hashes the exact rendered code-block text, not a normalized reserialization. Whitespace edits therefore invalidate previous source binding. `source.comment_id` is GitHub's comment anchor when available, or `description` for the PR/issue body. Description submissions additionally bind thread and form ID. Execution handlers must independently check the source and author; the extension never supplies an authenticated requester claim. PR head-SHA validation belongs to the future handler, not an invented value in a credential-free browser.

Discussion intent always disallows implementation. Approval is an approved-next-step request, not a discussion follow-up. When a session ID exists, the next execution should restore the originating session. A workflow run/attempt is distinct from session identity. An unmarked ordinary comment never triggers execution.

Choice answers normalize to `{optionId: boolean}`; text/notes are strings. Generated notes use `<question>_more_info` and `<question>_<choice>_more_info`. These are answer data, never template code. `next_instruction` and `additional_notes` remain distinct.

## Saved workflow snapshot (`github-workflow`)

Required: `kind: "workflow"`, `schema_version: 1`, `task_id`, `title`, `status`, ISO `updated_at`. Optional: `session_id`, `attempt_id`, ISO `started_at`, `run_url`, `dashboard_url`, `dashboard_status: "available" | "offline"`, `formula`, `gascity_version`, hex `head_sha`, `summary`, `beads` (default empty).

Status: `submitted`, `queued`, `running`, `needs-input`, `ready-for-review`, `failed`, `cancelled`, `done`.

Beads: `{id, title, status: "open" | "in_progress" | "blocked" | "closed", dependencies?: string[]}`. Overview uses the newest snapshot per task; Runs & beads retains every loaded snapshot. Timestamps are compared as instants (regardless of timezone offset); equality keeps the first loaded record. Saved state is not a guarantee a runner is still alive. Live links are private-tailnet navigation only, not embedded views. Invalid/credential-bearing URLs are never linked.

A future workflow should post immutable per-run snapshots and useful checkpoints, leaving a readable final/last-known comment after shutdown. Consumers must distinguish unverified comment claims from independently authorized execution state. Cross-browser reconstruction works through the same loaded GitHub comments without relying on local drafts.
